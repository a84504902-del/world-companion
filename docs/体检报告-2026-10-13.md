## 三、问题清单

### 🔴 P0-1 · API Key 明文裸奔 + 无鉴权 + 监听 0.0.0.0

**证据（实测）**：
```
$ curl http://localhost:8877/api/llms
{"llms":[{"id":"deepseek", ..., "api_key":"sk-d2b46e211a8e41beb6cab66ea3e6d1e9", ...},
         {"id":"agnes",   ..., "api_key":"sk-OvN0PpcIwGGkw9ygqMceJFVERi7L7YaFqkn9EMbNDmI1qhbt", ...}]}
```

**根因**：`routes/custom_llm.py` 的 `list_llms` 把 `api_key` 原样返回；`config.py:27` `HOST` 默认 `0.0.0.0`；全项目无任何鉴权中间件。

**后果**：同一 Wi-Fi 下任何人可 ① `curl http://<你的IP>:8877/api/llms` 偷走两把钥匙 ② 用 `/chat`、`/api/stt` 烧你的额度 ③ 用 `/history`、`/chat_sessions` 读走全部私人对话。

**修法**（三选一，可叠加）：
| 方案 | 工作量 | 说明 |
|---|---|---|
| 接口脱敏 | 10 分钟 | list_llms 返回 `sk-d2b4***d1e9`；测试连通性走单独的内部端点 |
| 访问令牌 | ~1 小时 | `.env` 加 `ACCESS_TOKEN`，中间件校验 `?token=` 或请求头；前端 fetch 统一带上 |
| 只绑本机 | 2 分钟 | `.env` 加 `HOST=127.0.0.1`，手机/局域网其他设备将无法访问（按需权衡） |

### 🟠 P1-2 · 重启服务后，首次打开页面历史空白（已实测复现）

**证据**：起了第二个实例（临时 DB 副本，库里 3 条消息）：
```
[重启后首次] /history -> 0 条   (数据库里实际有 3 条)
[点击切换后] switch_chat -> 3 条
[再拉一次]  /history -> 3 条
```

**根因**：`routes/chat.py:887` `history_handler` 只在**内存** `state.conversation_history` 非空时才读数据库；而 `app.py` 的 `main()` 启动时只设了 `_current_session_id`，**不加载历史**。刷新页面走 `/history` → 拿到空 → 界面全白，直到用户点一下左侧会话（`switch_chat` 会从 DB 加载）或发一条消息才恢复。

**连带影响**：离开 ≥2 小时生成的主动留言，在刚重启的会话里也可能不显示（`checkProactive` 重拉的还是同一个空 `/history`）。

**修法**：`history_handler` 改为无条件从 `db.load_messages()` 读（内存 state 只服务于增量追加）；或 `main()` 启动时加载。**~15 分钟，收益立竿见影。**

---

### 🟠 P1-3 · 会话单例：两个标签页就会串会话

**根因**：`chat_handler` 全链路用模块级全局 `_current_session_id`（`routes/chat.py` 出现 30+ 次），请求体**不带 session_id**；`/switch_chat` 改的是全局变量。后台任务（人物检测/关系检测）也用全局。

**后果**：两个标签页同时打开、或手机再开一个，后切换的会把前一个的「当前会话」改掉——消息写错会话、人物/关系分析串门。就是你快照里记的「会话隔离漏洞」，在 world-companion 仍在。

**修法**：`chat_handler` 接受请求体里的 `session_id`（前端 `state.currentSession` 早就带着，`/api/catchup` 已经是这么做的），全局只作兜底。**~1–2 小时，改动面大但机械。**

---

### 🟠 P1-4 · 历史漂移清洗硬编码 5 个人名 →「记不住前文」

**根因**：`llm.py:63`：
```python
if any(name in content for name in ['赵刚', '陈默', '周凯', '夏海', '沈青']):
    continue   # 整条消息丢弃
```
只要历史消息**提到**这 5 个名字（包括用户自己说的），整条从上下文里消失。切到沈青视角时，沈青相关的上下文正好被自己吃光。

**修法**：改为按「小说体叙述」特征清洗（如以 `角色名+道/说/笑` 开头的 assistant 消息），或按当前 `actor` 动态豁免名单。**~30 分钟。**

---

### 🟠 P1-5 · 每条消息 2–4 次 LLM 调用，两个后台检测零预过滤（成本）

**根因**：每发一条消息，后台跑 6 个任务，其中调 LLM 的：
| 任务 | 预过滤 | 模型 |
|---|---|---|
| 主回复 | — | 当前会话模型 |
| 场景提取 `scene.extract_scene` | **无，每条都调** | DeepSeek |
| 人物检测 `_detect_new_characters` | **无，每条都调** | DeepSeek |
| 关系检测 `_detect_relationships` | 仅「人物≥2」 | DeepSeek |
| 承诺抽取 `loops.extract_loop` | ✅ 有 `looks_like_promise` 关键词预判 | 当前会话模型 |

承诺抽取已经做了「不像承诺就不调」的优化，场景/人物/关系三个还是裸跑。按 DeepSeek 计费，闲聊一轮实际花 2–4 次调用的钱。

**修法**：给三个检测加节流（如每 3 轮跑一次 / 内容有变化才跑）+ 换成免费的 agnes 跑检测类任务。**~1 小时，直接省钱。**

---

### 🟡 P2-6 · 长会话全量渲染，无分页（待办#4，一直没做）

`chat.js:114 renderMessages` 全量拼 HTML 后 `innerHTML` 一次性替换；`/history` 返回全部消息。现在库里 1 个会话 0 条消息无感，按项目的聊法攒到几千条会明显卡。**修法：只渲染最近 200 条 + 上滚到顶加载更早的。~1.5 小时。**

### 🟡 P2-7 · 内存向量缓存无上限

`memory_retriever.py` 的 `_chunk_cache` / `_vector_cache` 全量常驻内存，每 3 轮对话加一个 chunk（384 维 float ≈ 5KB/条），只增不减。长期挂机会单调涨。**修法：加 LRU 上限或超量回退 DB 查询。~30 分钟。**

### 🟡 P2-8 · TTS 合成卡在响应热路径

`chat.py:614` 每条回复都 `await tts_synthesize(...)`（edge-tts 网络往返 1–2s），即使用户根本不点播放也合成，失败还静默。**修法：改后台合成，前端点播放时懒生成。~30 分钟。**

### 🟡 P2-9 · 删会话留孤儿数据（实测现存 9 行）

`delete_session`（`db.py:517`）清了 10 张表，但**漏了 `open_loops` 和 `scene_states`**（`pinned_memories` 有独立的 `delete_session_pins` 但删除路径未调用它，需确认）。实测当前库：
- `scene_states`：6 行，全部属于已删除会话
- `open_loops`：2 行 pending，属于已删除会话
- `summaries`：1 行，属于已删除会话

**修法：delete_session 补齐两张表 + 写个一次性清理脚本清历史孤儿。~20 分钟。**

---

### 🔵 P3-10 · 本机访问 `localhost:8877` 有 ~2 秒延迟（环境问题，非代码）

实测：`127.0.0.1:8877` → **13ms**；`localhost:8877` → **2038ms**。根因：本机代理栈拦截 IPv6 回环，`::1` 的拒绝连接要等满 2 秒，而域名解析先返回 `::1`。服务本身没问题（裸 aiohttp 对照 6–12ms）。
**建议：浏览器里用 `http://127.0.0.1:8877` 访问；README 注明。**（0 代码改动）

### 🔵 P3-11 · 无持久化日志

`log.py` 只配了控制台输出，重启即丢，出问题无据可查。**修法：加 RotatingFileHandler（logs/app.log，5MB×3）。~15 分钟。**

### 🔵 P3-12 · `.env` 明文密钥

git 层面安全（已确认未入库），但磁盘明文。要分享/截图项目时记得先脱敏。无需改动，提醒即可。
